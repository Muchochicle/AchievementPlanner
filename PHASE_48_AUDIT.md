## 3. Findings, ranked by severity × reachability × implementation value

### Finding 7 (NEW, HIGH severity, HIGH reachability, independently verified and reproduced) — The Session Planner permanently shows "0 planned" once every achievement in the current planned session is completed, even with other achievements still available

**Traced mechanism**, confirmed by reading `src/utils/planner/sessionManager.js:17-82` directly:

- `getSession(game, slug, duration)` first calls `loadSession(slug)` to read the persisted list of previously-planned achievement ids. When that list is non-empty (`sessionManager.js:37`, `if (stored && stored.length > 0)`), it takes over completely: it maps the stored ids to live achievements, drops any Steam has since confirmed complete (`:53-59`), and **returns that filtered result directly** — it never falls through to `createSession()` to rebuild a session from the game's still-available, not-yet-planned achievements, and never calls `saveSession()` again to update what's on disk.
- If **every** id in the stored session has since been completed (the natural, intended outcome of successfully using the feature), the filter at `:53-59` removes all of them and this branch returns `[]` — permanently. `localStorage["session-<slug>"]` still holds the old, now-fully-completed id list, so every future call to `getSession()` for this game repeats the exact same thing: filters an all-completed list down to `[]`, returns `[]`, never regenerates.
- **Reproduced directly** by tracing a concrete scenario against the real code: a game has 10 curated achievements; `getSession()` first picks 3 (ids 101/102/103) for a 45-minute session and persists `[101,102,103]` via `saveSession` (`sessionManager.js:69-78`). The player completes exactly those 3 on Steam — the intended, successful use of the feature — while 7 others remain unplanned. On the very next poll or reload, `stored = [101,102,103]` is still non-empty, so the top branch runs, filters out all 3 (now completed), and returns `[]`. `createSessionPlanner([], game)` (`src/components/session-planner/session-planner.js`) renders "0 achievements planned / 0/0 / 0%".
- **`getRecommendedAchievement(game)`** (`src/utils/planner/recommendation/recommendation.js`) is entirely independent logic (re-derives from `game.achievements` fresh every call, no stored-id cache) and correctly keeps recommending from the remaining 7 — so the Recommended Achievement card and the Session Planner card directly below it end up **contradicting each other**: one says "here's what to do next," the other says "nothing planned," at the exact moment the feature should feel most rewarding (right after finishing a planned session).
- The only two code paths that ever call `createSession()` again for an existing slug are `regenerateSession()`'s two real callers: the session-duration `<select>`'s `change` handler and the Recommended card's Skip button (`src/js/game.js:314-335,365-392`) — nothing regenerates automatically on the normal poll/refresh cycle (`renderSession()`, `game.js:396-419`, calls `getSession()` every time, which hits the same stuck branch every time).
- `src/utils/planner/sessionPlanner.js:21-48`'s in-memory `createSession()` cache has the textually identical bug pattern (a cache-hit branch that only re-filters previously-cached ids, never falls through to rebuild from `available`) — but tracing the actual call graph shows `sessionManager.js`'s own top-level `stored.length > 0` branch already intercepts every case where a *persisted* session exists and handles the filtering itself, without ever calling `createSession()` at all in that case. `createSession()` is only reached when `loadSession()` returns empty, and `getSession()` immediately persists whatever it returns — so on every subsequent call, `sessionManager.js`'s own branch takes over again. I could not construct a realistic call sequence where `sessionPlanner.js`'s own cache-hit branch is what actually produces a stuck-empty result (as opposed to `sessionManager.js`'s branch, which definitely does) — noting this as the same *pattern*, worth fixing for consistency/defense-in-depth alongside the real fix, not a second independently-reachable failure path.
- **Test-coverage check, confirmed directly**: `test/sessionManager.test.js:92-108` ("drops an entry from a persisted session once Steam confirms it completed") only completes *one of two* stored achievements, leaving the other — it passes today and would keep passing under the buggy code, since it never drives the stored list to fully empty. `test/sessionManager.test.js:214-228` ("still returns an empty session... when a game genuinely has no achievements left to plan") covers a game with **zero achievements from the very start** (`makeGame(slug, [])`), a different and already-correctly-handled case (Phase 41's fix). No existing test covers "a non-empty stored session, all of whose members later complete, while the game still has other, unplanned achievements" — confirmed by reading every test in the file.

**User impact**: this requires no rare precondition — it is the natural result of a player successfully using the Session Planner exactly as intended (plan a session, complete it). Every player who ever finishes a planned session on a game with more achievements left to plan hits this. Ranked above every other finding in this audit for that reason: no special account state, no storage failure, no library composition — just normal, successful use of the app's own core planning feature.

### Finding 4-refined (Phase 46/47's `/popular` fan-out, MEDIUM-HIGH severity, reachability corrected to HIGH for any logged-in user with a non-trivial Steam library) — Unbounded fan-out scales with the visitor's owned library size, not the 3-game catalog

Phase 46 and 47 both assessed this finding as "not currently reachable... would need a much larger catalog." **That assessment is incomplete** — re-tracing `buildGamesList()` (`backend/routes/games.js:121-152`), shared by both `GET /api/games` and `GET /api/games/popular`, shows it merges the visitor's **entire owned Steam library** (`ownedGames`, from a real `getOwnedGames(steamId)` call with no size cap) with the 3-game catalog, and `/popular`'s handler (`games.js:184-228`) fans out `getCurrentPlayerCount()` over **every game in that merged list with a valid appid** via a raw, unbounded `Promise.all` (`:192-206`) — not just the catalog games.

**Concrete, verified impact**:
- A logged-in visitor with, say, 500 owned Steam games (a common library size for anyone who's bought a few bundles/sales — not a rare "power user" edge case) triggers **500 simultaneous outbound HTTPS requests** to Steam's `GetNumberOfCurrentPlayers` endpoint on their *first* `/popular` load, each with its own `AbortController`/8-second timeout (`steamApi.js`'s `steamFetch`/`REQUEST_TIMEOUT_MS`).
- Each individual `getCurrentPlayerCount(appid)` result IS cached (2h success TTL, 30s failure TTL as of Phase 47) — so this burst is a real, but *repeatable-until-cache-fills* cost: every appid the visitor owns that Steam hasn't been asked about recently pays this again the next time their cache entries expire, not just once ever.
- `/api/games/popular` has **no rate limiting** at all — confirmed by reading `server.js:136-153`: `authRateLimiter` is `app.use`'d only ahead of `/auth/steam`; `app.use("/api/games", gamesRoutes)` has no limiter in front of it. Nothing stops a visitor (or a script) from re-triggering this burst repeatedly.
- The whole `/popular` response is only as fast as the *slowest* of the N concurrent requests — a single stalled/rate-limited Steam call among hundreds delays the entire response by up to the full 8-second timeout, for a page section (Home/Games "Popular") that has no particular reason to depend on the visitor's full library size at all.
- This directly parallels the *already-fixed* pattern in the same file: `attachAchievementAvailability()` (`games.js:42-116`) fans out over a comparable-or-larger set of games and deliberately uses `mapWithConcurrency(needsCheck, 8, ...)` (`games.js:56`) for exactly this reason — the `/popular` handler sitting right below it in the same file never got the same treatment.

**Assessment**: this is a real correction to two prior phases' severity assessment, not a new discovery of the underlying mechanism (Phase 46 already found and described the *code-level* inconsistency) — the new contribution here is verifying that the trigger condition is "any logged-in user with a non-trivial Steam library," which is common, not "the catalog grows," which hasn't happened and isn't imminent. Reachability is therefore HIGH today, for a large and normal population of real users, not a hypothetical future state.

### Finding 6 (NEW, MEDIUM severity, HIGH reachability, independently verified against the actual installed library source) — `express-session`'s default `MemoryStore` never prunes sessions created by an abandoned Steam login

**Traced mechanism**, confirmed by reading `backend/server.js:111-128`, `backend/controllers/steamController.js:14-32`, and the real installed `backend/node_modules/express-session/session/memory.js` directly:

- `app.use(session({...}))` (`server.js:119-128`) has no `store:` option, so `express-session` falls back to its own bundled `MemoryStore`.
- `MemoryStore` (confirmed by reading the actual module) has **no interval, timer, or background sweep of any kind**. `set()` (line 119) just writes to an in-process object. The *only* place an entry is ever removed for being expired is inside the private `getSession()` helper (lines 164-186), called only from `.get()`/`.all()` — i.e., only when that exact session ID is looked up again. An entry whose cookie is never presented again (the visitor never returns) simply stays in memory until the process restarts.
- `GET /auth/steam/login` (`steamController.js:14-32`) writes `req.session.oauthState = state` on **every single hit**, unconditionally. Since `saveUninitialized: false` only skips sessions nothing ever wrote to, this one write is enough to make `express-session` persist a brand-new session into the store on every hit — whether or not the visitor ever completes the OAuth round trip.
- The *successful* login path is correctly leak-free: `callbackWithDeps()` calls `regenerateSession(req)`, which (via `express-session`'s base `Store.prototype.regenerate`) destroys the old session before creating the new one — already covered by this suite's own passing `steamSessionRegeneration.test.js`. The leak is specific to **abandoned** logins: a visitor who hits `/login`, then closes the tab, cancels on Steam's consent screen, or is a bot/crawler with no cookie jar, leaves a permanent orphaned entry with nothing that ever calls `destroy()` on it.
- `server.js:111-117`'s own comment claims the 24h `SESSION_MAX_AGE_MS` "lets the in-memory session store actually prune expired sessions instead of growing without limit" — **this is incorrect for `MemoryStore`**, confirmed directly against its source above: `maxAge` only ever matters if the *same* session ID is looked up again post-expiry; it causes no active pruning of sessions that are never looked up again.
- `authRateLimiter` (`server.js:136-147`, 20 requests/15min per IP) bounds the *rate* from any single IP but not the *total* accumulated over the process's uptime — a slow, sustained trickle (crawlers, scanners, or a deliberately slow script spread across a few IPs, each staying under 20/15min) accumulates unboundedly over days/weeks.

**Concrete scenario**: a long-running production deployment with no periodic process restart gets routine background traffic to a public, unauthenticated GET endpoint (search crawlers and vulnerability scanners routinely probe `/auth/*`-shaped paths) — each hit creates and permanently retains a session object holding only a 64-character hex string. Given enough sustained time, this grows the process's resident memory without bound, eventually forcing an OOM kill or manual restart — which logs out every currently-logged-in user at once.

**Assessment**: real, precisely traced, no live-reproduction caveat needed (deterministic library behavior, not dependent on any external state) — but the actual *impact* requires sustained abuse or crawler traffic accumulating over a long uptime window to matter in practice; a low-traffic deployment restarted periodically (e.g. by a platform's own deploy cadence) may functionally never hit a problematic memory level. Ranked below Finding 7 and the `/popular` fan-out because the failure mode is slow-burn/operational rather than an immediately-reachable per-request bug, and below the two carried-over findings' *urgency* only in the sense that fixing it properly (introducing a real persistent/pruning session store) is the most structurally invasive change of any finding in this audit — see the scope discussion below.

### Finding 2 (carried over from Phase 46/47, still live, re-verified and expanded — LOW reachability, but confirmed can both crash and permanently stall the Game page) — localStorage write failures are unguarded across the whole player/inventory/session storage layer, not just `player.js`

Re-read `src/utils/player/player.js:107-117` directly: `savePlayer()` still has no try/catch around `localStorage.setItem`. Tracing the **full failure mode**, precisely, as asked:

- **Initial page load** (`game.js:140-260`): `syncAchievementCompletion(game, slug)` (`game.js:256`) can reach `savePlayer()` through `claimAchievement()` → `completeAchievement()` → `addXP()` (three separate, unguarded `setItem` calls per newly-completed achievement, `achievementManager.js:45-51`), and `addXP()` additionally calls `checkPlayerUnlocks()` → `unlockAvatar()` → `addItem()` → `saveInventory()` (`playerProgress.js`, `avatarUnlocks.js`, `inventoryManager.js`, `inventoryStorage.js` — a **fourth**, entirely separate storage key with its own unguarded `setItem`). All of this runs inside `init()`'s outer `try` (`game.js:140`); a synchronous `setItem` throw anywhere in this chain (Safari private-browsing `SecurityError`, or a real `QuotaExceededError`) is caught only by the outer `catch` (`game.js:469-493`), which **replaces the entire page with a generic "Something went wrong" message and never retries** — there is no path back to a working page short of a full reload, and if the underlying condition (e.g. a persistently full quota) doesn't clear, a reload hits the exact same crash again.
- **Poller-triggered updates** (`game.js:294-306`): the identical call chain runs inside the Phase-44 poller's `onResult` callback, which `poller.js:54-68` wraps in its own try/catch — this prevents a crash, but `saveProgress`, `refreshPlayerWidget`, and `refresh()` (`game.js:300-304`, all *after* the throwing line in the same callback) are silently skipped. Crucially, this **repeats identically on every subsequent poll for as long as the failure persists** — the poller's own bookkeeping (`deliveredRequestId`) is unaffected by a failed `onResult`, so it keeps polling forever, but every single poll hits the same `setItem` throw and silently no-ops the same way, forever. This matches the literal wording of the question asked: yes, this can make the page **permanently stop updating** without ever showing an error, for the rest of that session.
- **Newly confirmed, broader scope**: grepping every `localStorage.setItem` call site in `src/` (not just `player.js`) finds **6 unguarded call sites across 5 files** — `player.js:109` (`savePlayer`), `inventoryStorage.js:71` (`saveInventory`), `avatarStorage.js:11` (equipped-avatar id), `sessionStorage.js:26,68` (planned-session ids, session duration), and `planner/storage.js:30` (`saveProgress`). Every **read** site, by contrast, is already consistently guarded via the shared `safeParseJSON` helper (`src/utils/storage/safeJson.js`) — confirmed this exists and is used by `player.js`, `inventoryStorage.js`, and `sessionStorage.js`'s `loadSession`. There is currently no write-side equivalent (`safeSetItem` or similar) anywhere in the codebase — grepped and confirmed absent.

**Status: still open. Scope is now understood more precisely than Phase 46/47 left it** — this is a systemic, cross-cutting pattern (the write-side mirror of an already-solved read-side problem), not a one-off gap in `player.js` alone.

### Finding 3 (carried over from Phase 46/47, still live, re-reproduced — LOW-MEDIUM reachability, safest-fix approach now concretely validated) — Steam-game slug collisions

Re-reproduced directly against the current `mapSteamGame()`:
```
mapSteamGame({appid: 100001, name: "Call of Duty: Modern Warfare", ...}).slug
  === mapSteamGame({appid: 100002, name: "Call of Duty® Modern Warfare®", ...}).slug
  === "call-of-duty-modern-warfare"   (COLLISION: true)
```
unchanged from Phase 46/47's mechanism: the appid-canonical lookup (`getPlannerDataByAppId`, `plannerCatalog.js:76-102`) only resolves a slug via the catalog when the appid matches one of this app's 3 curated games; two arbitrary owned Steam games outside the catalog still collide on `derivedSlug` alone.

**New this phase — validated the "safest fix" question the user specifically asked**: the most obvious naive fix (always append the appid to `derivedSlug`, e.g. `${sanitizedName}-${appid}`, for every non-catalog game) was tested directly and found **unsafe**: `gameMapper.js:27`'s `getPlannerData(derivedSlug)` fallback — the path that resolves catalog data for a game matched *by name* rather than by appid — is live and reachable, confirmed by reproduction:
```
mapSteamGame({ appid: 999999 /* wrong/unmatched appid */, name: "Hades", ... })
  → { slug: "hades", hasPlanner: true, difficulty: 7 }   // correctly finds the real catalog entry by name
```
Changing `derivedSlug`'s formula globally would break this fallback for any catalog game matched this way (e.g. if a catalog JSON's `steamAppId` were ever missing/stale) — exactly the "breaking existing catalog-game canonical slugs" risk the user asked me to rule out. Today this fallback is not load-bearing for the 3 real catalog games specifically (all three have correct, live-verified `steamAppId` values — Hades 1145360, Portal 2 620, Hollow Knight 367520, confirmed by reading each JSON file directly), but it is real, tested-reachable code, not dead code, and a global formula change would silently degrade it.

**The safest fix, concretely**: detect and disambiguate collisions **post-hoc**, only where the full list of games being assembled is actually visible — inside `buildGamesList()` (`routes/games.js:121-152`) and `getGameDetail()`'s owned-game resolution (`gameDetail.js:54-63`) — appending the appid *only* to the slug(s) that actually collide, after mapping, rather than changing `mapSteamGame()`'s per-game derivation (and therefore the `getPlannerData(derivedSlug)` fallback) at all. This leaves every non-colliding case — which includes literally every catalog game and the overwhelming majority of real libraries — completely untouched, and only changes behavior in the rare case a real collision is detected.

**Status: still open, not addressed since Phase 46. Safest-fix approach for a future implementation phase is now concretely validated, not just proposed.**

## 4. Recommended Phase 48 scope

**Primary target: fix Finding 7 (the Session Planner regeneration bug) alone.**

| Finding | Reachability | Trigger precondition | Impact | Fix complexity |
|---|---|---|---|---|
| **7 — Session Planner stuck at 0** | Every player who finishes a planned session with achievements remaining | None — the natural result of successfully using the feature | Core planning feature silently breaks itself, contradicts the still-working Recommended card | Low — one function, one file, mirrors an existing pattern in the same file |
| 4-refined — `/popular` unbounded fan-out | Any logged-in user with a non-trivial Steam library | None — common library sizes trigger it | Slow/unreliable Home "Popular" section, real backend resource cost, no rate limit | Low — reuse `mapWithConcurrency`, already proven elsewhere in the same file |
| 6 — `MemoryStore` session leak | Any traffic to a public, unauthenticated GET endpoint | Sustained/repeated traffic over a long uptime window | Slow-burn memory growth → eventual OOM/forced restart, logs out all users | High — requires a real persistent/pruning session store, session-infra-wide change |
| 2 — localStorage write asymmetry | Rare | An actual `setItem` exception (quota/private-browsing) | Page crash (no retry) or permanent silent stall, now confirmed to span 5 files | Medium — new shared `safeSetItem` helper + 6 call sites |
| 3 — slug collision | Steam-library-dependent | Two owned games whose sanitized names collide | One game becomes permanently unreachable, no error shown | Medium — post-hoc disambiguation in 2 files, now concretely designed |

**Why Finding 7 alone, this phase:** it is the only finding in this audit that is reachable through *normal, successful* use of the app with zero special precondition — not a rare storage failure, not a specific Steam library composition, not sustained abuse over days. It directly undermines the app's own core value proposition (helping a player plan and complete achievements) at the exact moment that value should be most visible. The fix is small, self-contained to one file, and follows a pattern (`getSession()`'s existing "a stored `[]` must not be trusted" reasoning, `sessionManager.js:26-36`) already established and already tested in the same file — this is the lowest-risk, highest-value fix available from this audit.

**Why not bundle `/popular`'s fan-out fix in too**, even though it's also low-risk and self-contained: it's a different subsystem (backend Steam-API fan-out vs. frontend planner state) with no natural thematic overlap with Finding 7 — bundling them would be scope-inflation for its own sake, the same reasoning Phase 47 used to keep Findings 2/3/4 separate from its own scope. It is flagged here as a strong, ready-to-approve candidate for Phase 49 (or to fold into this phase if the user prefers, given how self-contained it is) rather than silently deferred.

**Why the `MemoryStore` leak is deliberately not proposed for this phase**: per this project's standing rule that security/session-infra-sensitive phases get extra scrutiny of the *whole* surrounding surface, not just the one line being changed — introducing a real session store (e.g. SQLite-backed, reusing the leaderboard DB already in `backend/services/leaderboardDb.js`) is a structural change to how every authenticated request in the app works, and deserves to be its own dedicated, carefully-scrutinized phase rather than a bolt-on to a frontend planner-logic fix.

**Findings 2 and 3 remain correctly deferred**, exactly as Phase 46/47 already reasoned — this audit sharpened their mechanism and fix design but did not change their reachability enough to promote them ahead of Finding 7.

### Exact implementation plan (for approval — not yet implemented)

1. **`src/utils/planner/sessionManager.js` — `getSession()`**: in the `if (stored && stored.length > 0)` branch, after computing the filtered (not-yet-completed) result, check whether it's now empty (`filtered.length === 0`) **and** whether the game actually has other, still-plannable achievements available (not completed, not skipped) — if so, fall through to the same `createSession()` + `saveSession()` path the "genuinely nothing stored yet" branch already uses below, instead of returning the stale `[]`.
