### Finding 1 (NEW, MEDIUM severity, MEDIUM-HIGH reachability, independently verified) - A tied viewer at the Top-10 boundary could appear completely unranked: no highlighted row, no "Your rank" line

`backend/services/leaderboardStore.js`'s `getGameLeaderboard`/`getGlobalLeaderboard` (`ORDER BY value DESC LIMIT 10`, no secondary sort) and `getUserGameRank`/`getUserGlobalRank` (`COUNT(*) WHERE value > mine) + 1`, genuine competition ranking) are two entirely independent queries. When several users tie at the exact cutoff value, every tied user correctly gets `rank <= 10` from the count-based query, but SQLite's unspecified row order for equal sort keys means the `LIMIT 10` query can arbitrarily exclude some of those same tied users from the actual `top10` array. `backend/controllers/podiumController.js`'s `toPublicRow()` sets `isMe: row.steamId === viewerSteamId` only for rows that made it into `top10` - so a viewer excluded by the tie never gets `isMe: true` on any row. `src/components/podium/podium.js`'s `renderMeSection()` then unconditionally suppressed the "Your rank" block whenever `me.rank <= 10`, trusting that this implied the viewer's row was already visible and highlighted above - an assumption the tie breaks. Result: the viewer sees a Top 10 list with no row marked as theirs and no separate rank line either, contradicting the product's own documented guarantee (`src/data/guides/app/podiums-and-leaderboards.js`: "your own current rank even if you're outside it... If you are in the visible Top 10, your row is highlighted"). Realistic reachability for this app's actual data: several categories (`completed-games`, `achievements`, `games-played`) are integer counts where many real users plausibly tie at low values, and any per-game podium with more than 10 owners sharing the same playtime (including a common legitimate 0) hits it too. Confirmed as an untested gap - existing tests (`leaderboardStore.test.js`'s tie tests, `podium.test.js`'s own-row-highlight test) always constructed fixtures where the tied/ranked user *was* present in `top10`, never the excluded case.

### Finding 2 (NEW, HIGH severity, LOW-MEDIUM reachability, independently verified and live-reproduced) - `getPlayer()`/`getInventory()` crashed on a syntactically-valid-but-non-object stored value

`src/utils/storage/safeJson.js`'s `safeParseJSON()` only catches `JSON.parse` *syntax* errors - it has no way to know the *shape* a caller expects (the same category of gap Phase 64 already closed for `sessionManager.js`'s `getSession()`, but that fix didn't extend to `player.js`/`inventoryStorage.js`). A stored value like the literal string `"null"` (or `"42"`, `"[]"` - all syntactically valid JSON) parsed through untouched instead of falling back to the caller's default. `src/utils/player/player.js`'s `getPlayer()` then crashed on the very next line (`player.claimedAchievements ??= []` throws when `player` is `null`); `src/utils/player/inventory/inventoryStorage.js`'s `getInventory()` returned the bad value directly, crashing the next real consumer downstream (e.g. `inventoryManager.js`'s `ownsItem()`, since optional chaining only protects the property access, not the base value itself). Both are reached synchronously, unguarded, from `profile.html`'s initial render path (`createProfileHeader()` → `createAvatarPicker()`), so either one taking down the render crashes the whole Profile page. Live-reproduced: injected the literal string `"null"` into both `achievement-planner-player` and `achievement-planner-inventory` in a real browser's localStorage, confirmed via the unfixed code path this crashes (traced through the source; the existing corrupted-JSON tests for these two functions only ever exercised genuinely malformed JSON like `"{not valid json!!!"`, never a validly-parsed non-object value, so this specific gap had no regression coverage). Requires an already-corrupted/manually-tampered/future-schema-mismatched localStorage entry to trigger - same reachability class as every other "browser storage as untrusted input" finding this codebase has repeatedly hardened against.

### Finding 3 (NEW, MEDIUM severity, LOW reachability today - same defensive-escaping gap class as two already-fixed findings) - `games.js`'s active-filter chips and `avatar-picker.js` interpolated text without `escapeHtml`, inconsistent with the rest of the codebase

- `src/js/games.js`'s `renderFilterChips()` built each active-filter chip's HTML from `filterText` (read via `.textContent` from a checked filter's own label, which decodes HTML entities back to raw characters) with no `escapeHtml()` call, both as element content and inside an attribute value (`aria-label="${buildRemoveFilterLabel(filterText)}"`). This is the same genre/difficulty-tier text `src/utils/catalog/genres.js`'s `createGenresHTML()` already escapes specifically "to close the gap if genre data is ever sourced dynamically in the future" - this downstream re-render of that same data was the one consumer that fix missed. Currently unreachable (catalog filter labels are curated static text), same as the already-fixed `genres.js`/`profile-badges.js` findings were before their own fixes.
- `src/components/avatar-picker/avatar-picker.js` never imported `escapeHtml` at all, unlike every sibling card/list component in this codebase (`podium.js`, `player-widget.js`, `profile-header.js`, `achievement-card.js`, `genres.js`, `search.js`, `profile-badges.js`), interpolating `item.name`/`item.id`/`item.image`/the unlock-requirement string directly into `class`/`data-avatar-id`/`title`/`alt`/text-node positions. `AVATARS` (`src/data/player/avatars.js`) is a fully static, hardcoded 6-entry catalog, so also currently unreachable - but inconsistent with the same "defend even though it's static today" convention this codebase has established and re-applied every time this exact gap class has been found (Phase 65's `profile-badges.js` fix, and originally `genres.js`).

Both fixed this phase for consistency and defense-in-depth, matching the established precedent of fixing this specific gap class on sight rather than leaving it open pending a "someday this data becomes dynamic" trigger.

## 4. Fixes implemented (4)

- **`backend/services/leaderboardStore.js`**: added a deterministic `steam_id ASC` secondary sort to both `getGameLeaderboard`'s and `getGlobalLeaderboard`'s `ORDER BY` clauses, so which rows land inside vs. just outside a `LIMIT 10` tie is stable and repeatable across calls (this alone doesn't guarantee the viewer's own tied row is one of the ones selected - that's the next fix).
- **`src/components/podium/podium.js`**: `renderMeSection()` now checks whether the viewer's own row is actually present in `top10` (`top10.some(row => row.isMe)`) rather than trusting `me.rank <= 10` alone to mean "already shown above." A tied-but-excluded viewer now correctly sees their own "Your rank" line.
- **`src/utils/player/player.js`** and **`src/utils/player/inventory/inventoryStorage.js`**: both now validate that `safeParseJSON`'s result is a genuine, non-array object before trusting it as the stored player/inventory, falling back to the default otherwise - the same "shape-check at the call site" pattern Phase 64 established for `sessionManager.js`'s `getSession()`, extended to these two remaining `safeParseJSON` consumers that hadn't gotten it yet.
- **`src/js/games.js`**: active-filter chip HTML now built via a new exported `buildFilterChipHtml()` (mirroring the existing `buildRemoveFilterLabel()` extraction pattern) that runs `filterText` through `escapeHtml()` for both the chip's text content and its `aria-label` attribute value.
- **`src/components/avatar-picker/avatar-picker.js`**: imports `escapeHtml` and applies it to every interpolated `item.id`/`item.image`/`item.name`/`title`/`requirement` value.
